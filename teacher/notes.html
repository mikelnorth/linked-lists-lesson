Introduction to Linked Lists

0:00 – 0:05 · 5 min

Goal: students can say "a linked list is nodes, each with data and a pointer to the next one" and know why we care.

Hook (before the script)

"Everyone has used an array. Suppose you have an array of a million items and you need to insert one new item at the very front. What has to happen to the other million?" (They all shift over by one.) "Today's data structure makes that a two-line operation, no matter how big the list is. The trade-off is what we are going to find out."

Script

Today, we're diving into the world of linked lists, a fundamental data structure in computer science.

Linked lists consist of individual elements called nodes. Each node holds two key pieces of information: the actual data we want to store and a "link" or pointer to the next node in the sequence.

Linked lists are particularly valuable when dealing with dynamic data, where the size and structure of the data can change during program execution. They allow us to efficiently manage and manipulate data without the limitations of fixed-size arrays.

In the upcoming slides, we will delve deeper into the structure, types, and applications of linked lists. Let's begin by understanding the basic structure of a linked list.

Slide 3

What is a Linked List? Basic Structure

0:05 – 0:10 · 5 min

Goal: vocabulary locked in: node, value, next, head, null.

Script

Now that we have a basic understanding of what linked lists are, let's dive into their structure.

At its core, a linked list is a sequence of elements called nodes. Each node contains two essential parts: the data itself and a reference, or a "link," to the next node in the list. Think of it like a treasure hunt, where each clue (node) contains the treasure (data) and a pointer to the next location (next node).

This structure allows for dynamic memory allocation, meaning that the linked list can grow or shrink as needed during runtime. We'll see later on how this differs from arrays, which have a fixed size.

You can see how each node holds some data and a pointer to the subsequent node. This chain of nodes linked together forms the linked list.

  3. "The word for 'the first node' is head. The word for 'there is nothing after me' is null."

"If I only hand you the head, how do you get to clue 3?" Follow next, then follow next again. There is no shortcut; that is the whole personality of this data structure.

As you can see in the diagram, the fundamental unit here is the node. Each node holds a piece of data, and importantly, a reference or a pointer to the next node in the sequence.

Slide 5

Types: Doubly Linked List

0:13 – 0:17 · 4 min
Script

Now, let's delve into another type of linked list: the doubly linked list.

In a doubly linked list, each node not only stores data but also maintains two references: one to the next node and another to the previous node. This bidirectional referencing allows for traversal in both forward and backward directions, offering more flexibility in navigating the list.

However, this added functionality comes at a cost. Doubly linked lists require more memory compared to singly linked lists because each node needs to store an additional pointer. This increased memory usage is the trade-off for the convenience of bidirectional traversal.

"What did we pay for the Previous button?" One extra pointer per node, and every insert or delete now has to fix two pointers instead of one.

Slide 6

Types: Circular Linked List

0:17 – 0:20 · 3 min
Script

Now, let's explore another type of linked list: the circular linked list.

In a circular linked list, the last node doesn't point to null; instead, it points back to the first node, creating a loop. This continuous structure allows for traversal without end.

Circular linked lists are particularly useful in applications like scheduling algorithms, where tasks need to be processed in a loop, or in managing playlists where the music should loop back to the beginning after the last song. We can think of a YouTube playlist with the repeat button on.

Do
  1. On the music player tab press Next until the last song, then once more: it stays put and the status says "already at the last song".
  2. Tick Repeat, press Next again: it wraps to the first song. "Repeat mode is circular behaviour. Our player fakes it with an if-statement; a true circular list makes the last node's next pointer literally point at the head."
Watch for

"How do you know when to stop traversing a circular list?" is a good question. Answer: you stop when you get back to the node you started on, not when you hit null, because you never hit null. (The visualizer on the page detects the loop the same way.)

Slide 7

Creating a Linked List in JavaScript

0:20 – 0:32 · 12 min · code-along

Goal: everyone has a working Node, LinkedList and add(), and has seen three boxes appear on their own screen.

Script

Okay, let's dive into how we actually create a linked list using JavaScript.

First, we need to define the basic building block: the Node. Each node will hold a piece of data and a pointer, which we'll call 'next', that points to the next node in the list.

Next, we'll create the LinkedList class itself. This class will contain methods for adding new nodes, removing existing nodes, and searching for specific nodes within the list.

This structure, the Node and the LinkedList class, is really the backbone for managing data dynamically.

Do: set the scene (1 min)

Show starter/linked-list.js. "This file is yours. The page already has buttons and a drawing routine; they call methods on your class. Right now the page says 'Step 2: define class LinkedList', because there is nothing here yet. Type along with me; after every step we save, refresh, and test."

Type: Step 1, the Node (3 min)
class Node {
  constructor(value) {
    this.value = value; // the data we store
    this.next = null;   // pointer to the next node. null = "nothing after me"
  }
}
  • this.next = null: every node is born as the last node. Something else will decide what comes after it.
  • Save, refresh, then in the console: const a = new Node(1); const b = new Node(2); a.next = b; a. Expand the object: a Node containing a Node. "That is all a linked list is. Objects pointing at objects."
Watch for

The browser already has a built-in Node (the DOM one). Declaring class Node at the top of the file shadows it, which is fine. If a student sees "Illegal constructor" they have not saved or refreshed and are calling the built-in one. The page prints a hint for this case.

Type: Step 2, the list (2 min)
class LinkedList {
  constructor() {
    this.head = null; // the only node the list remembers directly
    this.size = 0;
  }
}
  • Refresh: the page now draws head → null and the status turns green. "The list stores one pointer. Everything else is reachable by walking."
Type: Step 3, add(value) inside the class (5 min)
add(value) {
  const newNode = new Node(value);

  if (!this.head) {          // empty list: the new node IS the list
    this.head = newNode;
    this.size++;
    return this;
  }

  let current = this.head;   // start at the beginning...
  while (current.next) {     // ...and walk until the last node
    current = current.next;
  }
  current.next = newNode;    // hook the new node onto the end
  this.size++;
  return this;               // lets us chain: list.add(1).add(2)
}
  • if (!this.head): narrate the empty case first. "Special cases first is a habit that will save you in every linked list method."
  • while (current.next): we want to stop ON the last node, so we test whether there is a next one, not whether current exists. Compare with while (current), which would run off the end and leave current null.
  • current = current.next: this is the "follow the arrow" move. Say it out loud every time it appears today.
Checkpoint 1

Everyone: save, refresh, add 10, 20, 30 with the button. Three boxes, arrows between them, null at the end. Console: list.size is 3 and list.head.next.value is 20. Thumbs up before moving on.

Ask

"If the list had a thousand nodes, how many arrows does add() follow?" About a thousand. Appending is O(n) in this design. We will fix that in the music player with a tail pointer.

Common mistakes
  • Forgetting this. in front of head (ReferenceError: head is not defined).
  • Writing current.next = current.next or reassigning this.head inside the loop (the list loses nodes). Fix by re-reading: only the LAST line changes a pointer.
  • Defining add outside the class braces. The page will say "Not implemented yet: add()".
Slide 8

Operations: Insertion and Deletion

0:32 – 0:42 · 10 min · code-along

Goal: students can insert at the front in O(1) and delete by value, including the head special case.

Script

Now, let's delve into the fundamental operations we can perform on linked lists: insertion and deletion.

Insertion allows us to add new nodes to the list, and this can occur at the beginning, end, or even in the middle of the list. Deletion, on the other hand, removes nodes, either by specifying the value we want to remove or by indicating the position of the node in the list.

We just did "end". Let's do "beginning", which is the surprising one.

Type: Step 4, prepend(value) (3 min)
prepend(value) {
  const newNode = new Node(value);
  newNode.next = this.head;  // the new node points at the old first node
  this.head = newNode;       // and becomes the new first node
  this.size++;
  return this;
}
  • Order matters. Ask: "What breaks if I swap those two lines?" You overwrite head before saving it; the whole old list is unreachable.
  • No loop. "This is the two-line insert I promised in the hook. Same cost for a list of three or three million." Prepend 5 and watch it appear on the left.
Type: Step 5, delete(value) (6 min)
delete(value) {
  if (!this.head) return false;             // nothing to delete

  if (this.head.value === value) {          // special case: the head is the match
    this.head = this.head.next;
    this.size--;
    return true;
  }

  let current = this.head;
  while (current.next && current.next.value !== value) {
    current = current.next;                 // stop at the node BEFORE the match
  }

  if (!current.next) return false;          // walked off the end: not found

  current.next = current.next.next;         // skip over the matched node
  this.size--;
  return true;
}
  • Draw it before typing it. On the page: list 5 → 10 → 20 → 30. "To remove 20, who has to change? Not 20. The node before it: 10's next must jump to 30." That is why the loop stops one node early.
  • Head special case: nobody is "before" the head, so there is no node whose next we can rewire. We move head itself instead.
  • current.next && ...: the left side guards the right side. If current.next were null, reading .value on it would throw. Short-circuit evaluation is doing real work here.
  • Garbage collection: after current.next = current.next.next, nothing points at the removed node, so JavaScript reclaims it. No "free" call needed, which is a nice segue into slide 10.
Checkpoint 2

With 5 → 10 → 20 → 30 on screen: delete 20 (middle), delete 5 (head), delete 99 (returns false, nothing changes). Final picture: 10 → 30 → null, list.size is 2.

Common mistakes
  • Looping with while (current.value !== value) and then trying to unlink current. You are standing on the node you want to remove and cannot reach the one before it. Rewind to the drawing.
  • Forgetting the not-found case: the loop ends with current.next null and the next line throws "Cannot read properties of null".
  • Typing "20" vs 20 in the console: the page converts numeric input to numbers so === matches. From the console, pass a number.
If there is time: insert in the middle

Ask the class to describe insertAt(index, value) in words before showing solutions/linked-list.js: walk to the node before the slot, point the new node at what follows, point the previous node at the new node. "Same two-pointer shape as prepend, just further down the chain."

Slide 9

Operations: Traversal and Search

0:42 – 0:50 · 8 min · code-along

Goal: students see that every operation so far is the same loop, and can name its cost.

Script

Now that we've covered insertion and deletion, let's discuss how to traverse and search a linked list.

Traversal is the process of visiting each node in the list, starting from the head and following the 'next' links until you reach the end, which is indicated by a null value.

Searching involves traversing the list and comparing the value of each node with the target value you're looking for.

Type: Step 6, traverse(callback) (3 min)
traverse(callback) {
  let current = this.head;
  let index = 0;
  while (current) {                 // stops when current becomes null
    callback(current.value, index);
    current = current.next;
    index++;
  }
}
  • while (current) this time, not while (current.next): we want to visit the last node too, and stop when we fall off the end into null. Contrast with add().
  • The callback is "what to do at each stop". Console: list.traverse(v => console.log(v)), then press the page's traverse button, which uses a callback that collects values into the log.
Type: Step 7, search(value) (3 min)
search(value) {
  let current = this.head;
  while (current) {
    if (current.value === value) return current;
    current = current.next;
  }
  return null;
}
  • Same loop with an early return. "Traversal plus a question at each node."
  • Returns the node, not the value. Search for 30 on the page: the status shows Node { value: 30, next: null }. Search for 99: null.
  • Bonus if time (1 min): toArray() is traverse with a push. It is in the solutions and handy for the console.
Checkpoint 3 (end of part 1)

Console round-trip: list.add(40).prepend(1), list.search(40) is a Node, list.search(2) is null, press traverse. Anyone who is behind: tell them solutions/linked-list.js exists and they can paste it in now so they are ready for the exercise.

"Which of our methods needed a loop?" add, delete, traverse, search. Only prepend did not. "So what is the cost of finding the 500th item in an array vs in our list?" Array: one index lookup. List: 499 arrow-follows. That single sentence is the array-vs-list trade-off, and it is the next slide.

Slide 10

Memory Considerations: Linked Lists vs. Arrays

0:50 – 0:54 · 4 min
Script

Now, let's shift our focus to memory considerations when choosing between linked lists and arrays.

Linked lists employ dynamic memory allocation. This means that memory for each node is allocated during the program's execution. This dynamic approach allows linked lists to expand or contract as needed, providing a great deal of flexibility in managing memory.

Arrays, on the other hand, typically require a contiguous block of memory to be allocated at compile time. If the array size is overestimated, it can lead to memory wastage. Conversely, if the size is underestimated, reallocation might be necessary, which can introduce overhead.

Accuracy note: say this right after the script

"Now, you have all pushed onto a JavaScript array without declaring a size, so 'compile time' sounds wrong. It is describing languages like C. JavaScript arrays grow for you, but the engine does exactly what the slide describes behind your back: it keeps a contiguous block and, when it fills up, allocates a bigger one and copies everything over. You do not see it, you still pay for it. And inserting at the front still shifts every element."

Do: put this table on the whiteboard or say it out loud
OperationArrayLinked list
Get the item at index iO(1), jump straight thereO(n), walk from the head
Insert or delete at the frontO(n), shift everythingO(1), two pointer moves
Insert or delete in the middle (once you are there)O(n), shift the restO(1), rewire neighbours
Append at the endO(1) amortisedO(n) without a tail pointer, O(1) with one
Memory per itemJust the item, packed togetherItem plus one or two pointers, scattered around

"Nodes in a linked list also live wherever the engine put them, so the CPU cache likes arrays much more. In practice arrays win most of the time; linked lists win when you insert and remove a lot at known positions and rarely need 'the 500th item'."

    this.tail = null;      // last song. NEW: keeping this makes addSong() instant.

  • tail: "Remember add() walking the whole list? We are not doing that again. We pay one extra pointer on the list and get O(1) append." Refresh: status moves to "Step 3: write addSong".

Type together: Step 3, addSong (this is the hard one, go slow)
addSong(title, artist) {
  const song = new SongNode(title, artist);

  if (!this.head) {            // empty playlist: this song is everything
    this.head = song;
    this.tail = song;
    this.current = song;
  } else {
    song.prev = this.tail;     // 1. new song looks back at the old last song
    this.tail.next = song;     // 2. old last song looks forward at the new song
    this.tail = song;          // 3. the new song is now the end
  }

  this.length++;
  return song;
}
  • Narrate the three pointer moves with your hands: new song points back, old tail points forward, tail label slides over. Refresh: five seeded songs appear with prev/next cells, tail tag on the last one, first song highlighted as current.
  • Ask: "What goes wrong if step 3 comes before step 2?" this.tail.next = song sets the new song's own next to itself: a one-node loop. The visualizer will even show the loop arrow.

Solution for the four methods (reveal at 1:20) 
play() {
  return this.current;
}

next() {
  if (!this.current) return null;
  if (this.current.next) {
    this.current = this.current.next;
  } else if (this.repeat) {
    this.current = this.head;    // stretch: wrap around
  }
  return this.current;
}

previous() {
  if (!this.current) return null;
  if (this.current.prev) {
    this.current = this.current.prev;
  } else if (this.repeat) {
    this.current = this.tail;    // stretch: wrap around
  }
  return this.current;
}

playAll(callback) {
  let song = this.head;
  while (song) {
    callback(song);
    song = song.next;
  }
}
Discussion at the reveal (2 questions)
  1. "Why is previous() one line here, and what would it cost in our singly linked list from part 1?" Walk from the head until current.next is the current song: O(n). The prev pointer trades memory for speed.
  2. "Where did the circular linked list from slide 6 show up?" Repeat mode. The wrap-around is circular behaviour done with an if. A true circular list would set tail.next = head and need no special case at all, at the price of having to detect the loop when traversing.

Questions students tend to ask
"Why not just use an array? JavaScript arrays can do all this."

They can, and most of the time you should. The point is the cost model: arrays make index access cheap and front/middle inserts expensive; lists do the opposite. Also, many things that are not called "linked list" are built like one: DOM siblings (nextSibling, previousSibling), undo stacks, LRU caches, the task queue in schedulers.

"Where does a deleted node go?"

Once nothing references it, the garbage collector reclaims it. In C you would have to free it yourself; forgetting to is a memory leak. Keeping a stray reference to it in JavaScript is also a leak.

"Why does the class store size? Can't we count?"

Counting is O(n). Keeping a counter costs one increment per insert or delete and makes size O(1). Same reasoning as the tail pointer: spend a little memory to make a common question cheap.

"Is a doubly linked list always better than singly?"

No. It costs an extra pointer per node and every insert or delete must maintain two links, so there are twice as many ways to get it wrong. Use it when you actually need to go backwards.

"Can a node point to more than one next?"

Yes, and then it is no longer a list. Two children and it is a binary tree; any number and it is a graph. Nice preview of the next units.

"How does the picture on the page update?"

visualize.js walks from head following next every 200ms, exactly like traverse(), and redraws only if something changed. It keeps a Set of nodes it has seen so it can detect a loop instead of running forever.
